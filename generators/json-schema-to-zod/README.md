# json-schema-to-zod

[json-schema-to-zod](https://github.com/StefanTerdell/json-schema-to-zod)
2.8.1 with [zod](https://zod.dev) 4.6.6, both pinned exactly in
`package.json` / `package-lock.json`. `version` reads both out of the
installed packages and prints

```
json-schema-to-zod 2.8.1 + zod 4.6.6
```

which names `results/json-schema-to-zod-2.8.1-zod-4.6.6/`.

The tool is a *source-to-source* converter: `jsonSchemaToZod(schema)`
returns a string of code — one zod expression such as
`z.object({ "a": z.string().max(2) })`. There is no type to name, so the
contract's "call the root type `Root`" doesn't apply here; the expression
is bound to a module-local `schema`.

The package was marked unmaintained in March 2026. 2.8.1 is its last
release.

## Why zod 4

json-schema-to-zod can target either major (`zodVersion: 3 | 4`) and its
README says "By default, Zod v4 syntax is generated"; its own
`devDependencies` pin `zod@^4.1.3`. So the row runs the default: zod 4, no
`zodVersion` option passed.

That choice shows up in the results twice, and both are worth knowing
about:

- `z.literal(<array>)` means something different in zod 4. It is now a
  *set* of allowed literal values, not one literal that happens to be an
  array. json-schema-to-zod renders `{"const": [false]}` as
  `z.literal([false])`, which in zod 4 accepts the scalar `false` and
  rejects the array `[false]`. So the suite's
  `const with [false] does not match [0]` group rejects the one instance
  it should accept and correctly rejects the two it shouldn't. zod 3's
  `z.literal` compares with `===`, which would have rejected the array
  too: the bucket (🚧) is the same either way, and only the reason
  differs.
- `z.string().ip()` was removed in zod 4 (`z.ipv4()` / `z.ipv6()`
  replaced it), and `parseString` still emits it for `format: "ip"`,
  `"ipv4"` and `"ipv6"`. A schema that is *both* `type: "string"` and one
  of those formats therefore throws while the module loads, which the
  build step records as `compile_fail`. The suite never hits it, because
  its format tests omit `type` (see below), but a real schema would.

## Commands

```toml
version  = "node generate.mjs version"
generate = "node generate.mjs generate {out_dir}"
build    = "node build.mjs {gen_dir} {batch_dir}"
```

`deps.mjs` is a copy of quicktype's: `npm ci` on first use, the stdout
muzzle, and `writeAll` (a single `writeSync` to a non-blocking pipe stops
at 64 KiB and reports the short count rather than failing, which would
truncate a build result carrying hundreds of diagnostics). Generators do
not import across directories — a generator's source hash covers only its
own files, so a shared module would let an edit in one integration
invalidate another's stored results.

## generate

One long-lived node process reads the whole `[{key, draft, schema}]` array
and writes `<out_dir>/<key>.ts`:

```ts
// Generated by the bakeoff harness from json-schema-to-zod output.
import { z } from "zod";

const schema = z.string().max(2);

export function __conformanceCheck(json: string): void {
  schema.parse(JSON.parse(json));
}
```

Options passed to the tool: **none**. `module` defaults to `"none"` (just
the expression, no import, no export), `zodVersion` defaults to 4, and
`depth`, `withoutDefaults`, `withoutDescribes`, `withJsdocs` and
`parserOverride` are all left alone, so what the row measures is the tool
as it ships. Nothing is stripped from or rewritten in its output; the
expression is substituted verbatim.

`draft` is read off stdin and **ignored**: `Options` has no draft or
dialect field, and `$schema` isn't in the keyword table at all, so no
result can depend on it. The 2019-09/2020-12 relocations (`items` →
`prefixItems`, `dependencies` → `dependentRequired`, `$defs`) are simply
unknown keywords; draft 4's boolean `exclusiveMinimum`/`exclusiveMaximum`
works only because the number parser looks for that spelling explicitly.

`$ref` is **not** a keyword the dispatcher knows — there is no resolver
and no fetcher in the package. A schema whose root is a `$ref` falls
through to `z.any()`, local and `http://localhost:1234/...` alike. Nothing
is ever fetched; the `z.any()` is recorded like any other output. (The
README's own advice is to pipe the schema through `json-refs` first; doing
that would be measuring json-refs.)

Numbers in the *schema* are the one place the harness's exact digits can't
be kept: `jsonSchemaToZod` takes a parsed object, not text, so the schema
array arrives through `JSON.parse` and a bound like
`{"maximum": 1234...3031}` is already a float64 when the tool reads it and
is re-printed as `1.2345678910111214e+52` in the emitted expression. That
is what a user of the package gets too (its input is an object), so it is
the tool's rounding, not the glue's. Case data is a different matter and is
kept exact — see "The runner".

Status classification: the tool has no error type of its own. A throw from
a parser reading a keyword in a shape it didn't expect (`{"enum": 3}` →
`TypeError: schema.enum.every is not a function`) is the tool saying "I
can't do this", so it is `generation_error`; a `RangeError` (stack
exhausted) or the 30 s `Promise.race` timeout is `generation_panic`. On
the whole suite nothing hit either of the panic paths.

## build: there is no compiler

The emitted expression is JavaScript with a sprinkling of TypeScript —
`parseOneOf` writes an explicit type argument
(`schemas.reduce<{ errors: z.core.$ZodIssue[]; failed: number }>(...)`)
that plain JS cannot parse. All of it is *erasable* TypeScript, though, so
node 26 runs the `.ts` files directly with its own type stripping. There
is no `tsc` pass and no `typescript` dependency.

That is also the measurement we want. Running the output through `tsc`
would impose a type check the tool never promised to pass — its README
says the output "is not meant to be used at runtime" — and type errors
would land in `compile_fail` beside real breakage. The question is whether
the emitted source *runs*, so the build step is a **load probe**: import
each module once, by itself, and keep the ones that import cleanly. Two
things fail there, and both are `compile_fail` in the bakeoff's sense:

- the tool wrote source node can't parse;
- zod refused to *build* the schema the tool asked for (`.ip()`, a regex
  JS rejects, a `z.literal` of something unsupported) — the expression
  runs at module load, so this is a load failure, not a per-case one.

`probe.mjs <batch_dir> <start>` prints `{"ready": <start>}`, then imports
one key at a time and prints
`{"i": <index>, "r": "ok" | {"fail": msg}}`, flushed per line. `build.mjs`
spawns it, and if the process dies or stops making progress, blames the
one index that never reported and restarts past it — the same shape as the
harness's own runner loop, and the reason a module that exhausts the stack
inside zod is attributed to itself instead of sinking its neighbours. A
module that dies at load is distinguishable from a probe that never ran
only because of the `ready` line, so a probe without one is a hard
failure.

Two guards keep a broken environment from being recorded as the tool's
fault, since a `compile_fail` on every group in the suite would look like
a finding:

- a `__canary.ts` of our own (`import { z } from "zod"` and one
  `safeParse`) is run before the probe; if *that* doesn't load, nothing
  the tool wrote could either, and the build step exits non-zero;
- a probe that doesn't print `ready` is reported the same way.

The probe's time limit scales with the number of modules left
(60 s + 250 ms each) because `spawnSync` can only bound the whole process.
Measured cost is about 1 ms per module — 428 ms for 2020-12's 427 — so
that is two orders of magnitude of slack, which is the point: a flat cap
turns a loaded machine into spurious `compile_fail`s.

The batch directory gets a `package.json` with `"type": "module"` (so node
reads the `.ts` files as ESM) and a `node_modules/zod` symlink into this
directory's install, because `import { z } from "zod"` has to resolve from
a directory under `target/` that has no install of its own.

The runner is `<batch_dir>/runner.ts`, launched as
`[process.execPath, <abs path>]` — `process.execPath`, not `"node"` from
`PATH`.

## The runner

Protocol per DESIGN.md: `{"ready": start}`, then one
`{"case": {"i", "r"}}` line per case, flushed, with `writeSync` in a
short-write loop. A thrown `ZodError` (or anything else) is a `reject`; an
unknown key is a `panic` ("module not compiled"); only a dead process is a
panic, and that one the harness sees for itself. "Anything else" includes
a `RangeError` from a `superRefine` recursing too deep: JavaScript lets
you catch stack exhaustion, so it is a reject with
`Maximum call stack size exceeded` as its reason rather than a
`runtime_panic` — which is also what a caller of `schema.parse` would
see. The suite produces none.

Numbers reach the check as the suite's own digits: `cases.json` is parsed
with a `JSON.parse` reviver that keeps each number's `context.source`
text, and `rawStringify` puts it back verbatim, so `__conformanceCheck`
receives the original literal and does its own `JSON.parse`. Where
precision stops is then JavaScript's: a 50-digit integer is an `f64`
inside the module, which is what a user of this tool would get. Same
treatment as the quicktype TypeScript row.

A `ZodError`'s `message` is its whole issue list pretty-printed as JSON —
kilobytes per case in `results.json` — so the runner keeps the first three
issues as `path: message` and caps the text at 1000 characters.

## What zod actually enforces

Everything below is reached **only when the schema says `type`**.
`parseSchema` dispatches on `type` (and on `anyOf`/`allOf`/`oneOf`/`not`/
`enum`/`const`/`if`+`then`+`else`); a schema with no `type` and none of
those falls to `parseDefault`, which is `z.any()`. The JSON Schema Test
Suite almost always omits `type` when it is testing one keyword in
isolation — `{"maxLength": 2}`, `{"uniqueItems": true}`,
`{"properties": {...}}`, `{"format": "email"}` — so **960 of the 1587
modules the suite produces are exactly `z.any()`**, and that one fact is
most of the row's 🙈.

| keyword | emitted | enforced? |
|---|---|---|
| `type: string/number/integer/boolean/null/array/object` | `z.string()`, `z.number()`, `z.number().int()`, … | yes |
| `type: [a, b]` | `z.union([...])` | yes |
| `minLength` / `maxLength` | `.min(n)` / `.max(n)` | yes — zod 4.6 counts Unicode code points, which is what JSON Schema asks for (the suite never reaches it: those groups have no `type`) |
| `minimum` / `maximum` | `.gte(n)` / `.lte(n)` | yes |
| `exclusiveMinimum` / `exclusiveMaximum` (number, draft 6+) | `.gt(n)` / `.lt(n)` | yes |
| `exclusiveMinimum: true` (draft 4 boolean) | `.gt(minimum)` | yes |
| `multipleOf: 1` | `.int()` | yes, as integrality |
| `multipleOf: n` | `.multipleOf(n)` | yes (float remainder, so `0.0001` behaves like zod's) |
| `pattern` | `.regex(new RegExp(p))` | yes — **no flags**, see below |
| `minItems` / `maxItems` | `.min(n)` / `.max(n)` | yes |
| `uniqueItems: true` | `.refine(arr => arr.every((x,i) => arr.indexOf(x) == i))` | yes, by `indexOf`, so two objects with equal contents are both kept |
| `items: <schema>` | `z.array(...)` | yes |
| `items: [a, b]` | `z.tuple([a, b])` | positionally yes, but a zod tuple is *exactly* that long while JSON Schema's `items` array is a prefix, so a shorter instance is rejected; `additionalItems`, `minItems`, `maxItems` and `uniqueItems` are all dropped on this branch |
| `properties` + `required` | `z.object({...})`, non-required get `.optional()` | yes |
| `additionalProperties: false` | `.strict()`, or `z.record(z.string(), z.never())` with no `properties` | yes |
| `additionalProperties: <schema>` | `.catchall(...)` | yes |
| `additionalProperties` absent | plain `z.object({...})` | unknown keys stripped, i.e. accepted — correct |
| `patternProperties` | `.catchall(...)` + a `superRefine` loop over keys | yes |
| `enum` | `z.union([z.literal(v), ...])` | yes for scalars, no for arrays/objects |
| `const` | `z.literal(v)` | yes for scalars, no for arrays/objects |
| `anyOf` | `z.union([...])` | yes |
| `allOf` | `z.intersection(a, b)` | yes |
| `oneOf` | `z.any().superRefine(...)` counting passing branches | yes, exactly one |
| `not` | `.refine(v => !inner.safeParse(v).success)` | yes |
| `if`/`then`/`else` | `.superRefine` dispatch — **requires all three** | only with `else` present, and only when no `type` preempts the dispatch |
| `format` (on a `type: "string"`) | see below | partly |
| `default` | `.default(v)` | yes (and the property stops being required) |
| `description` / `readOnly` | `.describe(...)` / `.readonly()` | annotation |
| `$ref`, `$defs`, `definitions` | — | `z.any()` |
| `multipleOf` without a numeric `type` | — | `z.any()` |
| `propertyNames`, `minProperties`, `maxProperties` | — | `z.any()` |
| `dependencies`, `dependentRequired`, `dependentSchemas` | — | `z.any()` |
| `contains`, `minContains`, `maxContains` | — | `z.any()` |
| `prefixItems`, `unevaluatedItems`, `unevaluatedProperties` | — | ignored, so the schema is whatever its `type` says (`{"type": "array", "prefixItems": [...]}` is `z.array(z.any())`) |

### `pattern` and the `u` flag

`parseString` emits `.regex(new RegExp(<JSON-quoted pattern>))` — **no
flags at all**, so in particular no `u`. zod's `.regex()` then calls
`.test()`, which is an unanchored search, matching JSON Schema's
partial-match semantics. But without `u`, `\p{Letter}` is an Annex B
identity escape: `new RegExp("\\p{Letter}cole")` matches the literal text
`p{Letter}cole` and not `l'école`. That is what turns the suite's
`patterns always use unicode semantics` groups into 🚧 whenever the
pattern is reached through `patternProperties` (and 🙈 when it's a bare
`pattern`, which has no `type` and so never gets compiled at all). The
plain ECMA-262 regex groups — `\d`, `\w`, `\s`, control escapes, named
groups, lookbehind — all pass.

### `format`

`parseString` maps, and only on a `type: "string"` schema:

| JSON Schema `format` | zod |
|---|---|
| `email` | `.email()` |
| `uri` | `.url()` |
| `uuid` | `.uuid()` |
| `date-time` | `.datetime({ offset: true })` |
| `date` | `.date()` |
| `time` | `.time()` |
| `duration` | `.duration()` |
| `binary` | `.base64()` |
| `ip` / `ipv4` / `ipv6` | `.ip(...)` — **removed in zod 4**, throws at load |

Everything else (`hostname`, `idn-email`, `idn-hostname`, `iri`,
`json-pointer`, `relative-json-pointer`, `regex`, `uri-reference`,
`uri-template`) is dropped silently. It also maps
`contentEncoding: "base64"` → `.base64()` and
`contentMediaType: "application/json"` → a `.transform` that parses the
string, optionally `.pipe`d into `contentSchema`.

None of this is exercised by the suite: every schema under
`optional/format/` is a bare `{"format": "..."}` with no `type`, so it
compiles to `z.any()` and the whole section is 🙈 — except
`optional/format/unknown.json`, which is ✅ for the same reason.

### `const` and `enum` of non-scalars

`z.literal` compares values, so a `const` or `enum` member that is an
object never matches (`expected [object Object]`), and one that is an
array is reinterpreted by zod 4 as a set of literals (see "Why zod 4").
That is the bulk of the row's 🚧: `enum.json`, `const.json` and
`oneOf.json` hold 69 of the 107 false-reject groups, and 5 of the 9 🤪
on top of that.

### `oneOf` over untyped branches

`parseOneOf` emits a `superRefine` that counts how many branches
`safeParse` successfully — correct logic, but each branch is itself
compiled by the same type-dispatching parser, so an untyped branch becomes
`z.any()` and passes everything. `{"oneOf": [{"type": "integer"}, {"minimum": 2}]}`
becomes "exactly one of `z.number().int()` and `z.any()`", so a valid
integer is counted twice and rejected. 67 of the false-reject cases are
this single message, `Should pass single schema. Passed 2`.

### Integers past 2^53

`z.number().int()` in zod 4 means *safe* integer, so the bignum groups
report `Too big: expected int to be <=9007199254740991` on inputs the
suite calls valid. That is zod's bound, not the tool's.
